# 挖煤姬详情优先的自适应选品采集：设计规格

日期：2026-09-08
状态：已冻结旧采集，先离线验证再恢复真实浏览器轮询

## 1. 这次要解决的问题

选品广场的目标仍然是自动发现 CD 和实体游戏的价差，而不是要求用户逐个提供品番或 JAN。首页维持三栏对比信息流：左侧浅黄色为闲鱼可比样本，中间为成本、匹配和预计利润，右侧浅粉色为挖煤姬采购商品的实际详情页。

旧流程虽然有“打开详情页”的代码，但调度方式使它几乎不能完成有意义的验证。2026-09-08 对本机 SQLite 的只读复盘结果如下：

| 指标 | 实际值 | 说明 |
| --- | ---: | --- |
| 去重后的候选 | 945 | 搜索页发现的候选链接 |
| 挖煤姬详情已核验 | 22 | 只有 2.3% 到达采购证据阶段 |
| 已发出的闲鱼查询 | 211 | 其中很多发生在旧的详情优先修复之前 |
| 两侧都完成过检查 | 10 | 能形成完整比较的记录极少 |
| 同池同来源 URL 的历史重复组 | 42 | 旧身份键造成的重复排队 |
| 当前每池每轮详情预算 | 2 | 每 25 分钟最多两条，不能消化每页约 70–80 个候选 |

因此问题不是“市场一定没有机会”，而是采集器把大量搜索卡片当成了工作完成度，却没有建立详情页验证的持久队列。

## 2. 不变约束

- 不购买接口、代理、数据包或第三方商品流；不绕过验证码、风控或登录挑战。
- 采集只在本机已登录浏览器中低频、串行进行；Render 只保存可恢复副本和命令中继，GitHub Pages 只展示结果。
- 挖煤姬搜索结果页只负责发现 URL。任何机会在进入选品广场前，必须打开对应的挖煤姬详情页并验证标题、日元价格、可购买状态和核心商品完整性。
- 闲鱼搜索页是价格样本的候选来源；当一条记录通过初步利润阈值时，后续可选择打开 1–2 条闲鱼样本详情页做人工复核。搜索卡片不能被伪装为已验证成交价。
- 没有有效样本或没有利润是正常输出。系统不得为了填满广场生成或保留虚假的机会卡。

## 3. 目标流程

    低频挖煤姬搜索页
        -> 只保存候选 URL 和搜索页线索
        -> 全局详情队列
        -> 串行打开挖煤姬详情页
        -> 完整可购买：详情已核验
        -> 售罄、缺件：拒绝；解析失败：阻塞待查
        -> 按商品指纹分组的闲鱼队列
        -> 一次闲鱼搜索复用给同一商品的多个采购链接
        -> 样本清洗、成本和利润计算
        -> 三栏选品广场

### 3.1 候选状态

候选的生命周期状态和采集阶段分开保存，避免把“可见”误当成“核验完成”：

| 字段 | 取值 | 含义 |
| --- | --- | --- |
| status | active / expired / ignored | 采购链接的业务可用性 |
| pipeline_stage | search_discovered / detail_queued / detail_verified / resale_queued / resale_sampled / evaluated / blocked | 数据走到哪一步 |
| detail_verified | 0 / 1 | 只在挖煤姬详情页验证成功时为 1 |
| product_key | catalog: / jan: / 严格标题指纹 | 把同一商品的多个采购链接共用一组闲鱼查询 |

搜索页出现的数字、URL 参数、哈希或价格附近文字永远不能成为 JAN 或品番。只有详情页商品区域中显示的合理 JAN / 品番可成为精确检索键；没有精确标识时保留严格标题匹配，并降低置信度。

### 3.2 搜索页的类别门槛

搜索卡只是在排队前的线索，不能因为出现“初回限定”“限定版”“带付き”“稀有”等修饰词就被认定为 CD 或实体游戏。这些词只能帮助同类商品排序，不能证明商品本体。

- CD 池必须有 CD、Blu-ray、DVD、唱片、专辑、单曲、原声、进口盘等核心媒体信号，或有合理的详情页可复核品番/JAN；手机壳、数码配件、服装、包和其他已知非媒体品类一律排除。尤其 ``Dior CDロゴ`` 一类中的 ``CD`` 是品牌标志，不是唱片信号；只要同时出现时尚品牌或包、钱包、饰品等上下文，必须在详情队列前排除。
- 实体游戏池必须有游戏软件、卡带、光盘，或明确的平台加软件信号；主机、手柄、保护壳、攻略本、特典卡和空盒一律排除。
- 搜索页不能给出足够类别证据时，宁可不入队。广场的覆盖面来自持续的多关键词轮询，不来自把不相关商品塞进详情队列。

### 3.3 两个持久队列

1. 详情队列按采购链接去重，跨关键词、跨页面保留。每一轮先处理已有详情债务，再补充一个受上限控制的搜索页。新一页的 70 条卡片不能挤掉上一页尚未打开的 URL。
2. 闲鱼队列按详情页确认后的 product_key 分组。同一个品番、JAN 或等价标题的多个挖煤姬链接只发起一次闲鱼查询，再分别计算每个采购价的成本和利润。已完成评估的商品不会每轮重复查闲鱼；采购详情未变化时，最早每 180 分钟才回到闲鱼队列，以有限预算更新价格样本。

详情队列优先级只用于决定先看什么，不能替代详情证据：

1. 已有详情页确认的精确品番或 JAN；
2. 明确的 CD、游戏软件、限定版、稀有版等媒体信号；
3. 不含“仅特典、卡片、空盒、缺盘、主机本体”等排除信号；
4. 在同等证据下优先较低采购价和等待时间更长的链接。

当待核验详情队列超过高水位时，采集器暂停继续扩张宽泛搜索，而是先消化队列。这样“发现数”不会再掩盖“详情验证数”。

### 3.3 独立预算

不再让 candidate_budget 同时限制两个不同来源的昂贵步骤。每个池分别配置：

- search_card_budget：一次搜索页最多保存多少条合格链接；
- detail_budget：本轮最多打开多少个挖煤姬详情页；
- xianyu_query_budget：本轮最多查询多少个唯一商品指纹；
- queue_high_watermark：达到此详情债务量后只处理队列、不扩大搜索；
- 详情页失败会留下错误类型和次数，并将该 URL 标为 blocked；不会在未知页面质量下盲目重试。

第一次真实冒烟采用保守配置：每池一条关键词、详情不超过 4 条、闲鱼不超过 3 个唯一商品指纹。该数值只是结构验证上限；只有离线回放和冒烟数据证明质量稳定后，才扩大预算。

## 4. 自动停机与诊断

采集器必须在错误方向上自行停下，而不是继续累积无效抓取。每个批次记录以下阶段计数：

- 搜索页发现、进入队列、去重后的链接数；
- 详情尝试、详情验证、售罄或缺件拒绝、浏览器受阻；
- 唯一闲鱼查询、得到有效样本的商品指纹、完成评估、符合阈值的机会。

下列情形将把池置为 paused_quality，记录可读的暂停原因，并停止后续真实浏览器操作：

| 条件 | 动作 |
| --- | --- |
| 连续 2 个挖煤姬详情页出现安全验证、登录失效或重定向离开详情页 | 暂停该来源，保留已有结果，等待人工恢复登录或代码修复 |
| 一个最小质量窗口内已尝试至少 4 个详情页，详情验证率低于 50% | 暂停该池，提示关键词或卡片筛选需要重新设计 |
| 同批次中至少有 10 条合格卡片且 URL 重复率超过 5% | 暂停该池，先修复去重或解析器；不再继续查询闲鱼 |
| 闲鱼出现安全验证 | 维持来源级冷却，仍可在不扩大频率的前提下处理挖煤姬详情；不绕过验证 |

“详情核验成功但没有闲鱼样本”不会被误判为采集故障。系统会如实显示“无可比样本”，不制造机会；只有页面质量、去重或身份解析失真时才触发质量暂停。

## 5. 历史数据迁移

历史数据不删除：

- 对同一池、同一标准化来源 URL 的多条候选，保留详情证据更强、来源 ID 更稳定的一条作为规范行；
- 其余行标记为 ignored，关联的活跃机会标记为 expired，以免继续进入队列或出现在选品广场；
- 旧的 URL 派生 JAN、不合理目录号和未验证标识只保留为历史原文，不能作为后续闲鱼查询键；
- 本次详情队列恢复以前留下的、尚未打开详情页的搜索卡全部标记为 `quarantined` / `ignored`。它们仍保留审计记录，但不占用新采集的详情预算；新卡只会在该迁移完成后进入队列。
- 迁移必须幂等，并有测试证明不会删除 watchlist、市场商品或历史机会记录。

## 6. 可观察性与页面

首页的三栏对比布局保持不变。采集状态放入设置和运行日志，而不是覆盖选品广场：

- 池状态：运行中、冷却、paused_quality、需要人工处理；
- 本轮阶段漏斗：发现 -> 详情 -> 闲鱼 -> 评估 -> 合格；
- 队列深度、暂停原因和下一次可运行时间；
- 每张卡显示“挖煤姬详情已验证”，左侧闲鱼样本明确标为搜索样本或已打开详情样本。

## 7. 验收与恢复真实抓取的门槛

恢复真实浏览器前必须先通过以下本地测试：

1. 确定性回放：包含噪声搜索卡、重复来源 URL、同一商品的多个采购链接、售罄详情、缺件详情和两个有效闲鱼样本。
2. 无网络 worker 回放：使用注入的假 fetcher，确认命令、预算、冷却和暂停状态都不触发额外浏览器调用。
3. 受控真实冒烟：在已登录浏览器中，每池最多打开 4 个挖煤姬详情页、查询 3 个闲鱼商品指纹，保存详情 HTML、截图和运行计数。若触发质量门槛，立即停下并修复设计；即使结果为 0 个利润机会，也算如实完成。
4. 部署验收：本机 SQLite、Render 副本与 GitHub Pages 都显示相同的阶段状态；首页仍是左闲鱼、中央利润、右挖煤姬详情的三栏信息流。
