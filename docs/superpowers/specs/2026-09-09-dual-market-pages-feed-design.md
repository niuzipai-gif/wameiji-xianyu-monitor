# 双边选品信息流与 GitHub Pages 快照设计

**状态：** 已获版式确认，待规格审阅后实现
**日期：** 2026-09-09
**目标：** 让用户能用一个持续更新、可追溯的页面比较同一张 CD / GalGame 实体在闲鱼和挖煤姬的最低有效价格；左侧看闲鱼销售参考，右侧看挖煤姬采购详情，中间只显示有依据的匹配与利润结论。

## 1. 决策与边界

### 已确认的产品体验

- 首页的核心是**双列横向机会流**：桌面端一行两条比较卡，不是一条记录撑满整屏。
- 每张比较卡内部固定为：**左：闲鱼商品；中：同款判断 / 成本与利润；右：挖煤姬商品**。
- 两侧商品图、价格和进入原商品页的链接必须同时可见；图不是装饰，而是用户快速判断版本、腰封、特典和品相的证据。
- 中间区域必须显示同款键、核验条件与成本状态。实际代购费、转运、国际运费、包装、平台费缺失时，只显示“成本待输入 / 利润待算”，绝不以零或猜测填补。

### 数据真实性规则

一张可展示为“双边已核验”的卡必须同时满足：

1. 两端具有同一 canonical product key，至少包含品番 / JAN；存在版本、平台、品相、封膜、特典等差异时必须纳入键或拒绝配对。
2. 闲鱼侧保存的是当前最低有效**搜索挂牌价样本**，必须明确标注“下单前复核详情”；它不是成交价，也不伪装为详情核验。
3. 挖煤姬侧是当前最低有效的**详情已核验**价格，具有商品详情 URL、时间和商品图。
4. 每端都有原始公开 URL、抓取时间、价格、货币、商品图；任一项不满足，不进入双边卡。
5. 本机实时面板仅显示仍在有效期内的证据（当前规则为 180 分钟）。过期数据不参与可操作利润判断。

## 2. 页面信息架构

### 桌面端（≥1180px）

- 顶部保留简洁的搜索、刷新和采集暂停状态；英雄区压缩，不抢信息流空间。
- 指标行仅保留：已核验双边数、闲鱼证据类型、挖煤姬证据类型、利润状态。
- `#homeFeed` 为两列网格，列间距约 15px。
- 一张双边卡为紧凑横向卡，高度目标约 260–300px：
  - 左右来源区各占约 1 份宽度，包含来源标签、证据等级、商品主图、两行标题、价格和原链接；
  - 中部约 0.7 份宽度，展示锁定的同款键、两端价格关系、匹配理由和利润状态；
  - 主图保持可辨识的裁切，优先 `object-fit: cover`，但不拉伸；图片加载失败不能留下空白主卡。
- 卡的链接只打开对应商品源页，不触发购买、下单或扫码。

### 收窄桌面和移动端

- 1180px 以下：信息流退回单列，但每卡继续保持“左源 / 中间判断 / 右源”的横向结构，保障图片与价格的可比性。
- 760px 以下：中间判断区移到卡首；两个来源区按闲鱼、挖煤姬依次纵向排列。证据标签和原链接仍保留。
- 任何断点都不能以隐藏挖煤姬图片或将价格压成 `¥0` 的方式换取布局。

## 3. 本机与 GitHub Pages 的数据路线

```text
受控本机采集 / 人工复核
          │
          ├── SQLite + /api/dual-market/board（本机实时优先）
          │
          └── 通过质量门槛的发布导出
                    │
                    ├── web/data/dual-market-snapshot.json
                    ├── web/assets/dual-market/<snapshot-id>/*（公开商品图副本）
                    └── manifest（时间、来源数、SHA-256、图片映射）
                              │
                              └── GitHub Pages 静态站点
```

### 运行时读取策略

1. 本机页面先请求 `/api/dual-market/board`，并以其为唯一实时结论。
2. 当页面运行在 GitHub Pages、API 不存在或请求失败时，读取相对路径 `data/dual-market-snapshot.json`。
3. 静态快照显示“GitHub Pages 快照”、生成时间、卡数和快照状态；超过实时有效期后，只能作为历史参考，不能被写成“当前可买”或“当前利润”。
4. 若 API 和快照都不可用，展示诚实的空状态与故障原因；绝不把缓存的零值渲染为真实数据。

### 发布导出器

新增本机手动命令（实现名预定为 `scripts/export_dual_market_pages_snapshot.py`）：

- 只读取满足第 1 节门槛的比较记录；默认导出当前实时有效记录。
- 对每个来源图仅进行公开 HTTP(S) 下载，验证 MIME、非空文件、可解码图片和合理尺寸；落入 `web/assets/dual-market/<snapshot-id>/`。
- 输出 JSON 时将卡片的 `image_url` 改写为 Pages 内相对静态路径，同时可保留原始公开商品 URL 作为点击来源；不把会话、Cookie、请求头、原始 HTML、截图日志或访问令牌写入仓库。
- 任何卡的一侧图片下载 / 校验失败时，该卡不进入新快照；若所有卡失败，导出整体失败，保留上一份 Pages 快照而不发布空白卡。
- 以临时文件 + 原子替换写入 JSON、图片目录和 manifest，避免 Pages 看到半份快照。
- 快照必须是由一次明确的本机采集 / 人工复核产生；GitHub Actions 与 Pages 不运行采集器。

### 为什么当前不以远端实时后端为主

远端 API 需要部署、密钥、安全同步、常驻成本和运行监控。它可作为后续扩展，但在尚需持续验证双边抓取质量的阶段，会扩大故障面和数据泄漏面。GitHub Pages 静态快照能立即解决“页面有数据和图片”的问题，同时保留本机实时工作流。Docker 对未来自托管远端服务有用，但不是静态 Pages 或当前本机 API 的前置条件。

## 4. 前端数据契约

快照最少包含：

  "generated_at": "2026-09-09T00:00:00+08:00",
  "mode": "verified_static_snapshot",
  "summary": { "cost_pending_count": 0 },
  "cost_pending": [
    {
      "comparison_id": 0,
      "canonical_product_key": "catalog:...|edition:...",
      "xianyu": {
        "title": "...",
        "price": 0,
        "currency": "CNY",
        "url": "https://...",
        "image_url": "assets/dual-market/<snapshot-id>/xianyu-...webp",
        "evidence_level": "search_card",
        "captured_at": "..."
      },
      "wameiji": {
        "title": "...",
        "price": 0,
        "currency": "JPY",

## 5. 实现分段

1. **快照资产层：** 导出器、manifest、图片校验、脱敏约束和样本夹具。
2. **页面读取层：** API 优先、静态快照回退、来源 / 新鲜度标识和诚实空状态。
3. **信息流视觉层：** 双列网格、紧凑三段卡、图片兜底、响应式降级。
4. **验证与发布：** 单元测试、浏览器烟测、本机 9890 检查、Pages 部署后静态文件 / 图片 / 卡片内容读回验证。

## 6. 验收标准

- GitHub Pages 不依赖 `127.0.0.1` API 也能显示至少一份已发布快照的双边卡。
- 每张发布卡的两侧均为站内图片资产，均能加载；图片旁存在来源、证据等级、价格、抓取时间与源链接。
- 桌面宽度下第一屏能同时看到两张横向比较卡；卡不再按一条占用全宽 / 全高。
- 本机实时 API 保持优先；采集暂停时页面不会提交恢复或扫描命令。
- 静态快照超过新鲜度后显著标记为历史参考，且不产生“实时”“可买”“净利”误导。
- 利润只有成本输入完整且计算通过时显示；否则显示待算。
- 不提交 `data/local`、浏览器 profile、Cookie、访问令牌、原始详情页面或采集日志到 Git 仓库。
- 自动化测试涵盖：API 成功、API 不可用回退、空 / 过期快照、图片路径安全、导出器拒绝单边缺图、双列 DOM / CSS 关键契约。

## 7. 非目标

- 不在本次变更中启动云端实时采集、自动下单、自动登录、扫码或绕过人机验证。
- 不将闲鱼搜索挂牌价升级表述为成交价。
- 不根据不完整的成本输入生成利润推荐。
