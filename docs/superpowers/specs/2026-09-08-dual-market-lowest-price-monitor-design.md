# 挖煤姬 × 闲鱼双边最低有效价监控器：设计规格

日期：2026-09-08  
状态：用户已确认业务目标；真实采集继续暂停

## 1. 目标

这个项目不是泛选品榜，也不是“挖煤姬候选 + 闲鱼价格样本”的单向估价器。

它要持续寻找同一张 CD 或同一款 GalGame 实体，在两个市场的当前最低有效价格：

- **挖煤姬进货侧**：当前最低有效可买价；
- **闲鱼销售侧**：当前最低有效可售挂牌价；
- **中间利润层**：用进货侧的实际落地成本和销售侧的保守售价计算利润。

首页的每张完整机会卡固定为：

```text
[ 闲鱼最低有效售价的真实商品卡 ]
                 ↕
[ 同款身份、成本拆分、保守利润、证据状态 ]
                 ↕
[ 挖煤姬最低有效进货价的真实商品卡 ]
```

左侧为闲鱼销售侧，右侧为挖煤姬进货侧。两侧都必须显示真实商品图片、标题、价格、链接和采集时间。

## 2. 为什么现有方案必须替换

现有 `discovery_candidates` 以挖煤姬为主语，`xianyu_price_samples` 是可复用的价格池。它适合计算“某个商品的闲鱼参考价”，却不能证明页面右侧某一张闲鱼图就是和左侧采购品同一组证据。

可选路线如下：

| 路线 | 做法 | 结论 |
| --- | --- | --- |
| 在现有候选表上继续补样本绑定 | 为每个机会补一个 `xianyu_price_sample_id` | 不采用；底层仍是一侧主导，历史和新数据会继续混淆。 |
| 双边商品流 + 同款分组 + 最低有效价对比 | 两端各自保存商品观察记录，中间只配对同一个规范商品键 | **采用**；页面、采集和利润证据使用同一数据单位。 |
| 直接把原闲鱼监控项目完整复制两份 | 两套独立任务、独立结果、之后再另建比价层 | 不采用；会复制过多 UI、账号和调度逻辑，且不能天然解决跨站同款归组。 |

参考原闲鱼项目的只是“任务 → 商品记录 → 详情证据 → 结果”的数据所有权，不复制任何规避站点风控、模拟用户或绕过验证的行为。

## 3. 对称数据模型

### 3.1 商品观察记录

新增来源无关的 `listing_observations` 概念；一条记录只表示一个网站上一次真实可见商品观察，不表示市场均价，也不代表已配对机会。

每条记录至少保存：

- `source`：`xianyu` 或 `wameiji`；
- `source_listing_id`：该站商品 ID，仅用于本站去重；
- `canonical_product_key`：跨站同款键；
- 标题、媒体类型、版本、平台、品相、完整性说明；
- 商品价格、币种、已知运费或服务费；
- 商品 URL、实物图 URL、采集时间、截图/快照位置；
- 可售状态、详情是否已核验、证据等级和排除原因。

`source_listing_id` 永远不能用于跨站匹配。跨站键优先级固定为：

1. 详情页确认的品番；
2. 详情页确认的 JAN；
3. 经版本、平台、核心商品完整性同时验证的结构化标题键；
4. 其余记录进入待人工确认，绝不自动算利润。

### 3.2 同款分组和比较快照

`product_groups` 按 `canonical_product_key` 汇集两个来源的观察记录。`price_comparisons` 保存某次筛选出的双边最低有效记录及完整的计算输入；它不是从全局价格池临时拼出来的视图。

一个比较快照必须引用：

- 一条挖煤姬最低有效商品观察记录；
- 一条闲鱼最低有效商品观察记录；
- 两者的规范商品键和版本匹配证据；
- 已冻结的成本配置、汇率、售价、落地成本、净利润和利润率；
- 比较时间和两侧证据时间。

价格变动时创建新的比较快照，旧快照保留为历史，不覆盖。

## 4. “最低有效价”的固定规则

页面绝不把任意最低裸数字当作可用价格。两侧候选进入最低价排序前必须同时满足：

- 当前可见、可买或可售，且不是已售、预约、下架；
- 价格、标题、商品 URL、商品图齐全；
- 与商品组的媒体类型、版本、平台一致；
- 不是空盒、仅特典、仅卡片、缺盘、缺游戏本体、配件或明显损坏品；
- 价格可解析且没有异常占位值。

额外规则：

- 挖煤姬用于利润计算时必须是详情页已核验的商品；搜索卡只能进入待核验进货流。
- 闲鱼最低价初始可来自搜索卡，但必须标为“挂牌价样本”；若已打开详情页，则升级为“详情已核验”。
- 品相不同不默认等价：新品、未拆、二手完整、轻微瑕疵分别进入不同条件组；跨条件对比必须明确标记，默认不进入自动利润流。

## 5. 利润计算

默认使用保守的闲鱼最低有效挂牌价，而不是平均价、最高价或虚构成交价：

```text
预计净利 = 闲鱼最低有效售价 × (1 - 销售费率)
         - [挖煤姬商品价 × 汇率
            + 日本境内运费
            + 代理/服务费
            + 国际运费分摊
            + 国内转寄与包装
            + 售后与风险预留
            + 税费]
```

税费字段不得被系统假设为零；仅在用户实际、合法适用免税规则时，由成本配置显式设置为零。缺失成本输入时卡片显示“成本待确认”，不输出可采购结论。

## 6. 采集架构

两个采集适配器实现相同的输出契约：

```text
关键词 / 商品键
    → 当前网站可见搜索页
    → ListingObservation[]
    → 按本站商品 ID 去重、按跨站商品键归组
```

### 6.1 挖煤姬进货流

1. 搜索页只发现候选链接和初步图片/价格；
2. 按最低价和识别证据排序进入详情队列；
3. 只对队首少量商品打开详情页，确认价格、版本、完整性和实物图；
4. 合格详情参与最低有效进货价选择。

### 6.2 闲鱼销售流

1. 根据已确认的规范商品键搜索；
2. 保存当前可见的真实商品卡，含价格、图、标题、URL、品相线索；
3. 先在合格卡中选最低价；只有标题/版本不足以判断时才进入少量详情核验队列；
4. 不用未知来源的旧样本填充新商品的右侧卡片。

### 6.3 运行边界

- 第一阶段不启动定时任务、不恢复工作器、不发送浏览器操作；
- 真实采集恢复后也只允许用户明确发起的有上限批次；
- 每批次从一条同款开始，验证双边商品 ID、图片、版本、最低有效价和利润记录；
- 任一侧出现登录、验证、解析失真或图片/身份不一致时立即停止该侧，不扩大抓取。

## 7. 前端信息流

首页分为三个互不伪装的状态：

| 状态 | 显示内容 |
| --- | --- |
| 闲鱼待配对 / 挖煤姬待配对 | 单侧真实商品卡、最低价候选状态、缺少哪一侧证据。 |
| 待核验 | 已发现双侧，但最低价商品的版本、品相或详情尚未确认。 |
| 已比对利润流 | 两侧真实商品卡 + 中间成本、利润、匹配依据。 |

利润流不能因为没有完整卡就显示为空白；待配对和待核验流要明确显示数量、商品和下一步，不把它们伪装成机会。

## 8. 历史迁移

历史表和截图不删除。只有当历史挖煤姬记录和闲鱼样本已经有同一可验证的规范商品键、双边图片和各自 URL 时，才能转成新的比较快照。

其余历史记录保留为“未配对历史观察”，不猜测配对、不回填图片、不进入新的利润流。

## 9. 离线验收门槛

真实采集仍暂停，以下测试全部通过前不解除：

1. 同一品番的多条挖煤姬和闲鱼记录，能各自挑出最低**有效**价；
2. 空盒、仅特典、已售、无图、版本不符的更低价格不会被选中；
3. 任何一侧缺失时生成待配对状态，不生成利润；
4. 已配对记录引用的两个商品 ID、URL、图片均来自同一比较快照；
5. 成本缺失或利润为负时仍能显示事实，但不进入“值得收购”流；
6. 前端离线夹具能渲染闲鱼左卡、利润中栏、挖煤姬右卡；
7. 暂停状态下 worker、计划任务和浏览器适配器都不会被调用。

## 10. 实施拆分

1. **领域与存储层**：建立双边观察、商品组、比较快照以及最低有效价选择器；只使用夹具。
2. **服务层**：把现有两个浏览器适配器映射到同一个观察记录契约；保留暂停开关。
3. **API 与页面**：新建待配对、待核验、利润流读接口和三栏卡片；不复用旧的全局样本展示逻辑。
4. **受控冒烟**：仅在用户明确解除暂停后，以一个商品键验证一次完整双边记录；失败即自动停下并回到离线修正。
