# 选品偏好反馈层设计

## 目标

将用户对真实候选的产品偏好沉淀为可审计的本地反馈，而不把暂时的采购价、缺货或市场页面状态误当成产品好坏。现有的 125 个参考样本继续是正向参考；本期不伪造负样本，也不训练或启用自动淘汰模型。

## 边界

- 新反馈只关联现有 `discovery_candidates`，不修改参考样本、市场观察、价格、利润、机会决策或采集任务。
- 三种结果固定为 `keep`（保留）、`source_pending`（供应待找）和 `not_fit`（不符合）。前两种都是产品偏好正向信号；第三种才是负向偏好。
- 反馈是追加记录。每个候选用于汇总和未来评估时只取最新反馈，因此改判不会造成重复训练样本。
- 本期只提供采集、查看和“是否已经具备评估条件”的状态。不得自动购买、拒绝、隐藏候选、改写价格判断、发消息、启动浏览器或联网训练。
- 既有利润复核 `review_decisions` 不迁移、不复用：它描述一次机会的经营判断，不是用户的产品风格标签。

## 数据模型

新增本地 SQLite 表 `selection_preference_feedback`：

| 字段 | 含义 |
| --- | --- |
| `id` | 自增审计记录 ID |
| `candidate_id` | 已存在的发现候选 ID |
| `outcome` | `keep`、`source_pending` 或 `not_fit` |
| `note` | 可选、最大 500 字符的用户备注 |
| `created_at` | 本地写入时间 |

写入时必须验证候选存在、结果属于上述枚举、备注是文本且长度受限。读取“当前标签”时按 `created_at DESC, id DESC` 取每个候选最新的一条。统计同时返回全部事件数和去重候选数，避免把反复修改同一候选误算成更多训练证据。

`source_pending` 永远与供给问题分离：它不能变更候选的利润/风险/市场状态，也不能降低其参考匹配分数。

## 评估状态

反馈状态 API 返回三类当前标签数、总事件数、已标注候选数和评估门槛。门槛是至少 30 个不同候选，且至少 10 个正向偏好（`keep` + `source_pending`）与 10 个 `not_fit`。达到门槛后状态只显示 `ready_for_evaluation`，仍不自动上线分类器；未达到显示 `collecting_feedback`。

这个门槛是“可以评估下一阶段模型”的证据门槛，不是“已经训练成功”的声明。

## 服务和 API

在存储层增加独立的新增、列表和状态函数；所有输入边界在服务端验证。

- `POST /api/selection-feedback`：写入一条反馈，返回保存后的安全字段。
- `GET /api/selection-feedback?candidate_id=<id>&limit=<1..200>`：只读列出反馈；候选 ID 可选，limit 使用严格整数校验。
- `GET /api/selection-feedback/status`：只读返回当前样本结构和评估状态。

接口不返回外部 Cookie、原始页面、采购链接或任何自动决策。无效输入返回 400，不存在的候选返回 404，数据库错误返回不泄露内部路径的 500 错误。

## 看板交互

选品广场的机会卡（而非参考样本档案）显示三枚明确的反馈按钮：保留、供应待找、不符合。点击后仅调用本地反馈 API，刷新当前候选标签和顶部“偏好学习”统计。参考样本档案保持只读，继续只显示身份和市场证据，绝不出现价格、行动或购买/淘汰按钮。

接口不可用时，看板显示“偏好反馈暂不可用”，但不影响发现卡、参考档案和既有复核功能。

## 验证

- 存储测试覆盖枚举/候选/备注验证、追加审计、同时间戳时 ID 最新优先、正负分类统计和门槛。
- API 测试覆盖成功、坏输入、候选不存在、严格 limit 和数据库错误掩码。
- 前端契约测试覆盖三按钮只能出现在候选卡、参考样本档案保持无行动按钮，以及不可用回退。
- 跑反馈专项、现有参考记忆专项和全量 pytest；不会写入用户的真实候选反馈数据作为测试种子。

## 非目标

本期不做图片分类器、Embedding、外部模型调用、自动重排、自动拒绝、采购动作、外网检索或用户账号操作。后续只有在反馈达到评估门槛、并经用户明确确认后，才单独设计可验证的离线评估与训练流程。
